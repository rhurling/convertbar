# A re-queued new-name job whose output is already published is booked done

A connection can drop after finalize has run on the host but before ConvertBar heard back, so ADR 0003 re-queues a job whose work is in fact finished. When such a job is a new-name job, its source is now definitely gone, and its stored output name exists on the host, it is booked `done` from the host's stat of that output (`converted_size` from it, `space_saved` only when the original size is known), with its post-convert hook, and nothing is pulled or encoded. A plain re-run would book "Source file no longer exists" over a conversion that succeeded, and an error asking the user to check by hand would be just as wrong in the case that happens. Accepted gap: the file under the output name is not re-verified against the lost result, because its SHA was never stored. An in-place job never qualifies, since its source and output are one path; it re-converts, and skip-by-source-media covers that case.
